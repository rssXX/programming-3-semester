# Лабораторные работы: Bun + TypeScript + Elysia

Задания из методических материалов по Java / Spring Boot реализованы на своём стеке.
Все работы находятся в одном репозитории и одной ветке; этапы отмечены версиями API и комментариями.

| Работа | Реализация |
| --- | --- |
| ЛР1 | `/api/v1/hello`, `/api/v1/lists/*` — приветствие и коллекции |
| ЛР2–3 | `POST /api/v2/feedback` — модели, валидация, ошибки, модификация ответа и логирование |
| ЛР4 | `POST /api/v3/feedback` — изменение запроса и передача между двумя HTTP-сервисами |
| ЛР5 | `POST /api/v4/feedback` — годовая и квартальная премии, unit-тесты, рефакторинг контроллера |
| ЛР6 | `/api/v5/students`, `/api/v5/disciplines` — CRUD и файловая SQLite, слои controller / service / DAO / entity |
| ЛР7 | `/list`, `/groups`, `/actuator/*` — HTML-формы студентов и учебных групп, файловая БД и мониторинг |
| ЛР8 | `/lab8/*` — регистрация, вход, роли, сессии, CSRF и защищённые формы студентов |

## Установка и запуск ЛР4–5

```sh
bun install
```

В первом терминале запустить Сервис 2 (порт **8084**):

```sh
bun run dev:service2
```

Во втором терминале запустить Сервис 1 (порт **8082**):

```sh
bun run dev
```

В Windows PowerShell при запрете выполнения `bun.ps1` используйте `bun.cmd` вместо `bun`,
например `bun.cmd run dev`. Менять политику выполнения PowerShell не требуется.
Для запуска без наблюдения за файлами: `bun run start:service2` и `bun run start`.

OpenAPI: <http://localhost:8082/openapi> и <http://localhost:8084/openapi>.

## Как работает ЛР4

```text
Postman → Сервис 1 :8082/api/v3/feedback → Сервис 2 :8084/api/v3/feedback
            ↓                                 ↓
        ответ клиенту                 запрос и время передачи в логах
```

Сервис 1 логирует исходный запрос, выполняет валидацию ЛР3, затем применяет две реализации
`ModifyRequestService`: `ModifySystemNameRequestService` устанавливает `systemName = ERP`,
а `ModifySourceRequestService` — `source = Service 1`. Значение `ERP` выбрано из `Systems`
ЛР3: строка `Service 1` из Java-примера не прошла бы существующую валидацию `systemName`.
Остальные поля запроса сохраняются. Модификаторы создают копию объекта, поэтому исходный
запрос остаётся доступным для логирования ошибок.

`ForwardRequestService` отправляет изменённый JSON ровно один раз через HTTP `fetch`.
Сервис 2 использует тот же обработчик, модели и правила валидации ЛР2–3 и возвращает ответ,
но дальше запрос не пересылает. После успешного ответа Сервиса 2 Сервис 1 формирует свой
ответ клиенту. При недоступности Сервиса 2, его HTTP-ошибке или таймауте (5 секунд)
Сервис 1 возвращает HTTP 500 с `code = failed` и `errorCode = UnknownException`.
Невалидные и неподдерживаемые запросы возвращают HTTP 400 до пересылки.

Время приёма фиксируется в `onRequest`, до разбора JSON и валидации. Сервис 1 передаёт
свою метку в заголовке `x-service1-received-at`, а Сервис 2 вычисляет разность со временем
своего приёма и выводит её в миллисекундах вместе с `uid` и `operationUid`.
Метки хранятся отдельно для каждого запроса, включая параллельные запросы.
Поле `systemTime` из тела запроса для измерения не используется.

Измеряется интервал **от получения запроса Сервисом 1 до получения Сервисом 2**.
Время от нажатия Send до входа в Сервис 1 серверу неизвестно.
При запуске на разных компьютерах для сравнения меток нужны синхронизированные часы;
в данной работе оба процесса работают на одном компьютере.
Прямой запрос к Сервису 2 без метки допустим: в логах будет указано, что время недоступно.

Адрес получателя можно изменить переменной `SERVICE2_URL`. Например, в PowerShell
перед запуском Сервиса 1:

```powershell
$env:SERVICE2_URL = 'http://localhost:8084/api/v3/feedback'
bun.cmd run dev
```

## Проверка через Postman

Импортировать [коллекцию ЛР4](postman/lab4.postman_collection.json) и выполнить её при
запущенных обоих сервисах. Проверки ЛР2–3 находятся в
[исходной коллекции](postman/feedback.postman_collection.json).

Пример `POST http://localhost:8082/api/v3/feedback` с `Content-Type: application/json`:

```json
{
  "uid": "message-4",
  "operationUid": "operation-4",
  "systemName": "CRM",
  "systemTime": "2026-10-28T12:00:00.000Z",
  "source": "Postman",
  "communicationId": 100,
  "templateId": 8,
  "productCode": 1500,
  "smsCode": 10
}
```

Ожидается HTTP 200, `code = success`, пустые `errorCode` и `errorMessage`.
В логах Сервиса 1 исходный запрос содержит `CRM` и `Postman`, а в логах Сервиса 2
полученный запрос содержит `ERP` и `Service 1`. Пример строки времени:

```text
[Service 2 / LR4] Transfer time (uid=message-4, operationUid=operation-4): 7 ms
```

Число миллисекунд зависит от конкретного запуска.
Для проверки сбоя остановить Сервис 2 и повторить корректный запрос к Сервису 1: ожидается HTTP 500.

## ЛР5: расчёт премий и unit-тесты

Запуск обоих сервисов остаётся тем же. Новый маршрут Сервиса 1:
`POST http://localhost:8082/api/v4/feedback`. Маршруты `/api/v1`, `/api/v2` и `/api/v3`
сохраняются. Сервис 1 рассчитывает премии, затем пересылает запрос в Сервис 2 по правилам
ЛР4; получатель обрабатывает известные ему поля feedback. Сбой получателя даёт HTTP 500.

К исходному JSON добавлены обязательные поля `position`, `salary`, `bonus`, `workDays`:

```json
{
  "uid": "message-5",
  "operationUid": "operation-5",
  "systemName": "CRM",
  "systemTime": "2026-10-28T12:00:00.000Z",
  "source": "Postman",
  "communicationId": 100,
  "position": "HR",
  "salary": 100000,
  "bonus": 2,
  "workDays": 243,
  "year": 2023
}
```

`year` — дополнительное необязательное поле для воспроизводимого расчёта; без него
используется текущий год сервера. `bonus` — множитель, а `workDays` — отработанные дни
за расчётный год, от 1 до 365 либо 366. Зарплата и множитель должны быть неотрицательными.

Формула из рисунка 2 методички:

```text
annualBonus = salary × bonus × daysInYear × positionCoefficient / workDays
```

Число дней определяется по правилу високосного года 4/100/400.
Для приведённого примера `annualBonus = 360493.8271604938`, `quarterlyBonus = null`.
Для 2024 года с теми же данными `annualBonus = 361481.48148148146`.
Результат сохраняется как число без округления, как в Java-примере.

| position | Должность | positionCoefficient | isManager |
| --- | --- | --- | --- |
| DEV | Разработчик | 2.2 | false |
| HR | Специалист по персоналу | 1.2 | false |
| TL | Руководитель команды | 2.6 | true |
| PO | Владелец продукта | 2.8 | true |
| TPM | Технический продакт-менеджер | 3.0 | true |
| CTO | Технический директор | 3.5 | true |

Коэффициенты DEV/HR/TL взяты из задания. Коэффициенты PO/TPM/CTO в нём не заданы:
указанные значения приняты в рамках работы и отмечены комментарием в коде.
Формула квартальной премии также не задана; принят равномерный расчёт
`quarterlyBonus = annualBonus / 4`. Метод проверяет `isManager` и отклоняет вызов для
DEV/HR. Контроллер рассчитывает им только годовую премию и возвращает
`quarterlyBonus = null`. Для TL в 2023 году квартальная премия — `195267.48971193415`.

Проверки данных выполняются до пересылки. При ошибке — HTTP 400 с прежним контрактом
ошибки, без полей премий. Правило `uid = 123` сохранено.

Модели Request и Response снабжены комментариями и описаниями для OpenAPI.
Расчёты находятся в отдельных сервисах, а формирование ответов и обработка ошибок
вынесены в общий `FeedbackResponseService`. Контроллер ЛР5 содержит регистрацию
HTTP-маршрута и делегирует обработку прикладному сервису.

- [Сервисы расчёта премий](src/routes/v4/feedback/bonus.ts), [должности](src/routes/v4/feedback/enums.ts), [модели](src/routes/v4/feedback/model.ts).
- [Контроллер](src/routes/v4/feedback/index.ts), [прикладной сервис](src/routes/v4/feedback/service.ts), [общие ответы](src/routes/v2/feedback/response-service.ts).
- [Unit-тесты](tests/lab5-bonus.test.ts) и [HTTP-тесты](tests/lab5-api.test.ts).
- [Postman-коллекция ЛР5](postman/lab5.postman_collection.json).
- [Отчёт Markdown](otchet/lab5.md) и [отчёт DOCX](otchet/РИЗ-250213у-Романов-Сергей-Лр5.docx).

## ЛР6: REST API и база данных

H2 и Spring Data JPA из методички заменены на SQLite и встроенный драйвер
[`bun:sqlite`](https://bun.sh/docs/runtime/sqlite). Отдельный сервер БД и новые npm-зависимости
не нужны. Контроллеры, сервисы, интерфейсы DAO и сущности разделены по файлам в
[src/routes/v5](src/routes/v5). Код отмечен комментариями «ЛР6».

Для ЛР6 достаточно **Сервиса 1**, Сервис 2 используется в ЛР4–5:

```sh
bun install
bun run db:init
bun run db:seed
bun run start
```

`db:init` создаёт таблицы, `db:seed` добавляет демонстрационные записи и не дублирует их
при повторном запуске. Заполнение необязательно. Без `db:init` схема создаётся автоматически
при первом обращении к CRUD. База сохраняется в `testdb/students.sqlite` и исключена из Git.
Изменения остаются после перезапуска. Путь можно переопределить перед запуском и командами БД:

```powershell
$env:DATABASE_PATH = 'testdb/my-students.sqlite'
bun.cmd run db:init
bun.cmd run start
```

Для просмотра БД в DBeaver создать подключение **SQLite** и выбрать абсолютный путь
к этому файлу. Скрипты [schema.sql](src/database/schema.sql) и [seed.sql](src/database/seed.sql)
также можно выполнить через SQL-редактор. Предыдущие API не открывают файл БД.

Базовый адрес: `http://localhost:8082`. Вместо `/api/students` из отдельного Java-проекта
используется `/api/v5/students`, поскольку работы хранятся вместе. OpenAPI:
<http://localhost:8082/openapi>, JSON: <http://localhost:8082/openapi/json>.

| Метод | Студенты | Учебные дисциплины | Результат |
| --- | --- | --- | --- |
| GET | `/api/v5/students` | `/api/v5/disciplines` | Список, включая пустой |
| GET | `/api/v5/students/{id}` | `/api/v5/disciplines/{id}` | Одна запись |
| POST | `/api/v5/students` | `/api/v5/disciplines` | Создать, HTTP 201 |
| PUT | `/api/v5/students` | `/api/v5/disciplines` | Заменить поля записи; `id` в JSON |
| DELETE | `/api/v5/students/{id}` | `/api/v5/disciplines/{id}` | Удалить, вернуть `id` |

Тело POST студента (`id` назначает БД):

```json
{ "name": "Иван", "surname": "Иванов", "faculty": "ИТ", "age": 25 }
```

Тело POST дисциплины (поля второй таблицы выбраны в рамках работы):

```json
{ "name": "Базы данных", "hours": 108 }
```

Для PUT добавить `id` существующей записи к полному набору её полей. Текст обрезается
по краям; пустые строки запрещены. Ограничения студента: имя до 15 символов, фамилия
до 25, факультет до 20, возраст — целое число 0–150. У дисциплины название до 100 символов,
часы — целое число 1–10000. `id` — положительное безопасное целое число.

Каждая операция возвращает `success`, `message`, `data`. Пример создания:

```json
{
  "success": true,
  "message": "Студент создан",
  "data": { "id": 1, "name": "Иван", "surname": "Иванов", "faculty": "ИТ", "age": 25 }
}
```

Успешные GET / PUT / DELETE возвращают HTTP 200, невалидные данные — 400,
отсутствующая запись при GET / PUT / DELETE — 404, ошибка БД — 500.
При ошибке `success = false`, `data = null`, `message` объясняет результат;
технические подробности пишутся только в серверный лог. PUT не создаёт отсутствующую запись.
Параметризованные запросы в DAO передают пользовательские значения отдельно от SQL.

Импортировать [коллекцию Postman ЛР6](postman/lab6.postman_collection.json) и выполнять
папки сверху вниз вручную или через Collection Runner. В коллекции 28 запросов:
полный цикл CRUD обеих сущностей, проверка сохранённых изменений, 400 и 404.
`studentId` и `disciplineId` сохраняются автоматически после POST, поэтому фиксированные
идентификаторы не нужны. Проверки удаляют только созданные ими записи.

```sh
bun test tests/lab6-api.test.ts
bun test tests/lab6-database.test.ts
bun test
bun run typecheck
```

23 теста ЛР6 используют реальные HTTP-серверы и временные файловые БД: проверяются
CRUD обеих таблиц, валидация, повреждённый JSON, ошибки БД, независимость таблиц,
сохранение данных после перезапуска, повторное заполнение и наличие маршрутов в OpenAPI.
Пользовательский файл БД при тестировании не изменяется.

Код: [контроллер студентов](src/routes/v5/students/index.ts),
[контроллер дисциплин](src/routes/v5/disciplines/index.ts), [подключение БД](src/database/index.ts).
Отчёт: [Markdown](otchet/lab6.md), [DOCX](otchet/РИЗ-250213у-Романов-Сергей-Лр6.docx).

## ЛР7: веб-формы студентов и учебных групп

Задание из `labs/2023_2024__Spring_Boot__Laboratornaya_rabota_7.docx` реализовано
в том же приложении на Bun + TypeScript + Elysia + SQLite. Серверные HTML-шаблоны
заменяют Thymeleaf. Новые файлы находятся в `src/routes/lab7` и отмечены «ЛР7».

```powershell
bun.cmd install
bun.cmd run db:init
# Необязательно: добавить демонстрационных студентов, дисциплины и группу
bun.cmd run db:seed
bun.cmd run start
```

В браузере открыть **<http://localhost:8082/list>** — студенты,
**<http://localhost:8082/groups>** — учебные группы. Корень сайта перенаправляет
на список студентов. Для ЛР7 достаточно Сервиса 1; Сервис 2 не требуется.
Команда `bun.cmd run dev` запускает тот же сервер с наблюдением за файлами.

| Метод | Студенты | Учебные группы | Назначение |
| --- | --- | --- | --- |
| GET | `/list` | `/groups` | Таблица записей |
| GET | `/addStudentForm` | `/addGroupForm` | Пустая форма |
| GET | `/showUpdateForm?studentId=1` | `/showGroupUpdateForm?groupId=1` | Форма редактирования |
| POST | `/saveStudent` | `/saveGroup` | Создание или изменение по скрытому `id` |
| POST | `/deleteStudent` | `/deleteGroup` | Удаление по `studentId` / `groupId` в форме |

Формы отправляются обычным браузерным POST (`application/x-www-form-urlencoded`).
После сохранения и удаления сервер отвечает 303 и перенаправляет на список:
обновление страницы не повторяет запись. Удаление выполняется кнопкой с POST.
При ошибке ввода возвращается HTML с HTTP 400, введёнными значениями и подсказками;
отсутствующая запись даёт 404, ошибка БД — 500.

Студенты используют тот же сервис и таблицу, что и `/api/v5/students` из ЛР6:
изменения через браузер видны через API и наоборот. В SQLite добавлена таблица
`study_groups`: `id`, название `name` (1–30 символов), `faculty` (1–20 символов)
и `course` (целое 1–6). Поля групп выбраны в рамках работы, поскольку методичка
их не задаёт. Связь со студентами не требуется заданием и не добавлялась.
Существующий файл БД дополняется новой таблицей при первом обращении без удаления
данных. `DATABASE_PATH`, DBeaver и команды БД работают так же, как в ЛР6.

Аналог Spring Boot Actuator реализован собственными диагностическими маршрутами:

| Адрес | Что возвращает |
| --- | --- |
| `/actuator` | Ссылки на методы мониторинга |
| `/actuator/health` | Состояние SQLite: `UP` (200) или `DOWN` (503) после реального `SELECT 1` |
| `/actuator/info` | Название приложения, номер работы, стек, версия Bun, время запуска приложения |
| `/actuator/metrics` | Имена доступных метрик |
| `/actuator/metrics/process.uptime` | Время работы процесса Bun в секундах |
| `/actuator/metrics/process.memory.usage` | Память процесса (RSS) в байтах |

Все адреса доступны на `http://localhost:8082`. Коллекция
[Postman ЛР7](postman/lab7.postman_collection.json) содержит проверки страниц
и шести диагностических запросов. Для требуемых 3–5 скриншотов мониторинга
можно выбрать любые пять адресов из таблицы.

```powershell
bun.cmd test tests/lab7.test.ts
bun.cmd test
bun.cmd run typecheck
```

Проверяются CRUD обеих сущностей через реальные HTTP-формы, валидация и экранирование,
общие данные с ЛР6, добавление таблицы в существующую БД, сохранность после перезапуска,
мониторинг и ошибки БД. Используются временные файлы; пользовательская БД не меняется.

Отчёт: [Markdown](otchet/lab7.md), [DOCX](otchet/РИЗ-250213у-Романов-Сергей-Лр7.docx).
Скриншоты не создавались: в отчёте оставлены места для самостоятельной вставки.

## ЛР8: регистрация, вход и разграничение доступа

Задание из `labs/2023_2024__Spring_Boot__Laboratornaya_rabota_8.docx` адаптировано
к Bun + TypeScript + Elysia + SQLite. Аналог Spring Security реализован в
`src/routes/lab8`; код помечен «ЛР8». Используются прежние сервис/DAO студентов,
общие HTML-шаблоны с параметрами и локальные стили.

```powershell
bun.cmd install
bun.cmd run start
```

Открыть **<http://localhost:8082/lab8>**, зарегистрироваться, затем войти по email
и паролю. После входа открывается список студентов. В навигации доступны
«Студенты», «Пользователи» и кнопка выхода. Готовых аккаунтов и паролей нет.
Сервис 2 не требуется; `bun.cmd run dev` также поддерживается.

| Адрес | Доступ и назначение |
| --- | --- |
| `GET /lab8`, `/lab8/index` | Публичная главная страница |
| `GET /lab8/register` | Форма регистрации |
| `POST /lab8/register/save` | Создание пользователя, успех → 303 на страницу с сообщением |
| `GET /lab8/login`, `POST /lab8/login` | Форма входа и проверка учётных данных |
| `GET /lab8/list` | Список студентов после входа |
| `GET /lab8/addStudentForm` | Форма добавления после входа |
| `GET /lab8/showUpdateForm?studentId=1` | Форма изменения после входа |
| `POST /lab8/saveStudent`, `/lab8/deleteStudent` | Сохранение и удаление после входа |
| `GET /lab8/users` | Список зарегистрированных пользователей, требуется `ROLE_ADMIN` |
| `POST /lab8/logout` | Завершение сессии и очистка cookie |

Как в листинге `UserServiceImpl` из методички, при регистрации назначается
**`ROLE_ADMIN`**. Связь пользователей и ролей реализована отдельной таблицей
`user_roles` (many-to-many). Проверка роли `/users` выполняется на сервере
при каждом запросе. Пароли хешируются через `Bun.password` с **Argon2id** вместо
BCrypt из Java-примера; в HTML и списке пользователей паролей и хешей нет.
Имена и фамилии сохраняются отдельно, email нормализуется и уникален без учёта
регистра. Длина пароля — 8–128 символов.

Для ЛР8 автоматически создаётся **отдельный файл `testdb/lab8.sqlite`**:
таблицы `users`, `roles`, `user_roles`, `sessions`, а также таблица студентов.
Данные этого этапа доступны через защищённые маршруты `/lab8/*`.
Маршруты и данные ЛР1–7 сохраняются по прежним адресам. Новая ветка не создаётся.

Путь задаётся отдельно от `DATABASE_PATH`:

```powershell
$env:LAB8_DATABASE_PATH = 'testdb/security.sqlite'
bun.cmd run start
```

`DATABASE_PATH` и `LAB8_DATABASE_PATH` должны указывать на разные файлы.
Для проверки таблиц в DBeaver выбрать **SQLite** и файл ЛР8. Создание схемы
происходит при первом запросе к `/lab8`; повторный запуск сохраняет данные.
Отдельный SQL-скрипт или демонстрационный аккаунт для запуска не требуются.

Сессии хранятся в SQLite и живут 8 часов. Cookie `lab8_session` содержит случайный
токен и имеет `HttpOnly`, `SameSite=Lax`, `Path=/lab8`; при HTTPS добавляется `Secure`.
В БД хранится SHA-256 токена. При входе сессия и CSRF-токен меняются, при выходе
сессия удаляется. Все POST, включая регистрацию, вход и выход, проверяют скрытый
CSRF-токен. Поэтому сначала нужно открыть соответствующую форму и сохранить cookie;
обычный браузер выполняет это автоматически. GET не удаляет данные и не завершает сессию.

Анонимный запрос защищённой страницы перенаправляется на вход (303), недостаточная
роль или неверный CSRF дают 403, неверные учётные данные — 401, ошибки полей — 400,
отсутствующий студент — 404, ошибка БД — HTML 500 без технических подробностей.

Для проверки в Postman импортировать [коллекцию ЛР8](postman/lab8.postman_collection.json)
и выполнить сверху вниз в Collection Runner. Она ведёт cookie, извлекает CSRF,
генерирует уникальный email, проверяет регистрацию, вход, полный CRUD студента,
ограничения доступа и выход. Автоматические перенаправления в запросах выключены,
чтобы проверять исходные статусы. Студент удаляется в конце; созданный учебный
аккаунт остаётся в БД.

## Автоматические проверки

```sh
bun test
bun run typecheck
```

Интеграционные тесты запускают два настоящих HTTP-сервиса на свободных портах и проверяют
изменённый запрос, отсутствие повторной пересылки, логирование времени, параллельные
запросы, ошибки валидации, недоступность / HTTP-ошибку / таймаут получателя и сохранение маршрутов ЛР1–3.
ЛР5 дополнительно проверяет годовой и квартальный расчёты, все должности, високосные
и вековые годы, запрет квартальной премии для неуправленческих должностей и расширенную валидацию API.
ЛР6 проверяет CRUD обеих таблиц, ответы об успехе и ошибке, валидацию, параметризацию SQL,
повторное заполнение демонстрационных данных и сохранность записей после перезапуска.
