## Цель работы

Доработать веб-приложение, реализовав регистрацию, вход, выход и разграничение доступа на основе ролей. Сохранить пользователей, роли и связи между ними в базе данных, обеспечить хранение хешей паролей и доступ к операциям со студентами после аутентификации.

## Описание задачи

Методическое пособие предлагает Spring Boot, Spring Security, Spring Data JPA, H2 и Thymeleaf. Как и в предыдущих лабораторных, работа выполнена на собственном стеке проекта: TypeScript, Bun, Elysia и SQLite. Все этапы находятся в одном репозитории и ветке main; новые файлы размещены в src/routes/lab8 и отмечены комментариями «ЛР8».

Необходимо реализовать сущности пользователя, роли и студента; отношение пользователей и ролей «многие ко многим»; слой доступа к данным, DTO и сервисы. Клиентская часть должна включать главную страницу, регистрацию, вход, список пользователей, список и форму студентов. Главная и регистрация доступны анонимно; для работы со студентами требуется вход, а для списка пользователей — роль администратора. После выхода защищённые страницы должны стать недоступны.

### 3. Создание и настройка базы данных

Общие таблицы учебного журнала создаёт ApplicationDatabase. Дополнительную схему пользователей и сессий применяет SecurityStore. Оба скрипта выполняются идемпотентно, через CREATE TABLE IF NOT EXISTS, при первом обращении. Повторный запуск не удаляет записи. Включена проверка внешних ключей.

Листинг 1. Схема аутентификации (src/routes/lab8/schema.sql, ограничения длины в полном файле):

```sql
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    first_name TEXT NOT NULL,
    last_name TEXT NOT NULL,
    email TEXT NOT NULL COLLATE NOCASE UNIQUE,
    password_hash TEXT NOT NULL
) STRICT;
CREATE TABLE IF NOT EXISTS roles (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE
) STRICT;
CREATE TABLE IF NOT EXISTS user_roles (
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role_id INTEGER NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, role_id)
) STRICT;
CREATE TABLE IF NOT EXISTS sessions (
    token_hash TEXT PRIMARY KEY,
    user_id INTEGER REFERENCES users(id) ON DELETE CASCADE,
    csrf_token TEXT NOT NULL,
    expires_at INTEGER NOT NULL
) STRICT;
```

Таблица user_roles реализует many-to-many: пользователь может иметь несколько ролей, а роль — принадлежать нескольким пользователям. Для регистрации создаётся роль ROLE_ADMIN, как в листинге UserServiceImpl из методички. Роль не берётся из пользовательского поля формы.

Имя и фамилия хранятся отдельно, поэтому составные имена не разбиваются по пробелам. Email нормализуется к нижнему регистру. UNIQUE с COLLATE NOCASE запрещает создание двух учётных записей с одинаковым email в разном регистре. Сохранение пользователя и связи с ролью выполняется в одной транзакции.

### 4. DTO и регистрация

Публичный User содержит id, firstName, lastName, email и roles. RegistrationDTO дополнительно принимает пароль. UserCredentials используется только при проверке пароля и содержит passwordHash. Пароль и хеш не передаются в шаблон списка пользователей и объект сессии.

Форма регистрации проверяет обязательность имени и фамилии, длину до 50 символов, корректность email до 254 символов и пароль длиной 8–128 символов. Повторный email возвращает форму с сообщением возле поля. При ошибке текстовые значения сохраняются, а пароль снова вводится пользователем.

Листинг 2. Основные действия регистрации (src/routes/lab8/service.ts):

```typescript
const email = data.email.trim().toLowerCase()
if (this.dao.findByEmail(email)) {
    throw new DuplicateEmailError('На этот email уже зарегистрирована учётная запись')
}
const passwordHash = await Bun.password.hash(data.password, 'argon2id')
return this.dao.create({
    firstName: data.firstName.trim(),
    lastName: data.lastName.trim(),
    email,
}, passwordHash)
```

В полном коде дополнительно обрабатывается конфликт UNIQUE при одновременной регистрации: один запрос создаёт пользователя, второй получает понятную ошибку. После успеха сервер возвращает HTTP 303 на /lab8/register?success=1; на странице выводится подтверждение. Регистрация сама по себе не выполняет вход.

### 5. Вход и серверные сессии

Пользователь вводит email и пароль. UserService находит учётную запись и проверяет пароль через Bun.password.verify. Неизвестный email и неверный пароль дают одинаковое сообщение «Неверный email или пароль» и HTTP 401. Для неизвестного email также выполняется проверка хеша.

Cookie lab8_session содержит случайный 256-битный токен. В таблицу sessions записывается SHA-256 токена, а не его исходное значение. Срок действия — 8 часов. У cookie установлены HttpOnly, SameSite=Lax и Path=/lab8; при HTTPS дополнительно устанавливается Secure.

Листинг 3. Ротация сессии при успешном входе (src/routes/lab8/index.ts):

```typescript
const created = sessions.create(user.id, session)
cookie[SESSION_COOKIE].set({
    value: created.token,
    httpOnly: true,
    sameSite: 'lax',
    path: '/lab8',
    maxAge: SESSION_SECONDS,
    secure: new URL(request.url).protocol === 'https:',
})
return redirect('/lab8/list', 303)
```

При входе прежняя анонимная сессия удаляется, токен и CSRF-токен меняются. Просроченная или поддельная cookie не даёт доступ. При выходе сервер удаляет сессию из БД и отправляет cookie с Max-Age=0. Повторное использование старой cookie после выхода невозможно. Пользователи, роли, студенты и непросроченные сессии сохраняются после перезапуска.

### 6. Разграничение доступа и защита форм

| Маршрут | Доступ |
| --- | --- |
| GET /lab8, /lab8/index | Все посетители |
| GET /lab8/register, POST /lab8/register/save | Все посетители, для POST нужен CSRF |
| GET /lab8/login, POST /lab8/login | Все посетители, для POST нужен CSRF |
| GET /lab8/list | Вошедшие пользователи |
| GET /lab8/addStudentForm, /lab8/showUpdateForm | Вошедшие пользователи |
| POST /lab8/saveStudent, /lab8/deleteStudent | Вошедшие пользователи с CSRF |
| GET /lab8/users | Пользователи с ROLE_ADMIN |
| POST /lab8/logout | Вошедшие пользователи с CSRF |

Листинг 4. Защита списка пользователей (фрагмент src/routes/lab8/index.ts):

```typescript
.get('/users', ({ session }) => session.user!.roles.includes('ROLE_ADMIN')
    ? html(usersPage(users.findAll(), session))
    : html(errorPage(403,
        'Для просмотра пользователей требуется роль администратора.',
        session), 403), { detail })
```

Проверка входа применяется к группе защищённых маршрутов до выполнения обработчика. Аноним направляется на /lab8/login. Роли загружаются из БД при каждом запросе, поэтому изменение роли действует и для уже открытой сессии. Скрытие ссылки в меню дополняет проверку на сервере.

Все POST проверяют скрытое поле _csrf, связанное с текущей сессией. Это относится также к регистрации, входу и выходу. Отсутствующий, неверный или чужой CSRF-токен даёт HTTP 403 без изменения данных. Сравнение токенов выполняется timingSafeEqual. GET не выполняет удаление или выход.

Пользовательские строки экранируются перед выводом в HTML. SQL параметризован. Заголовки Cache-Control: no-store, X-Content-Type-Options, X-Frame-Options и Content-Security-Policy задаются для новой версии приложения. Ошибки БД дают HTML 500 с общим сообщением; технические детали остаются в серверном логе.

### 7. Веб-формы и операции со студентами

Главная страница содержит ссылки на вход и регистрацию. После входа навигация показывает имя пользователя, список студентов, список пользователей при наличии ROLE_ADMIN и кнопку выхода.

Форма регистрации содержит имя, фамилию, email и пароль. Форма входа содержит email и пароль, а также выводит сообщения о неверных данных и успешном выходе. Список пользователей показывает только имя, фамилию, email и роли.

Студенческие страницы используют сервис и DAO из ЛР6 и шаблоны из ЛР7 с адресами /lab8. Доступны добавление, список, редактирование и удаление. Скрытый id определяет создание либо обновление. После успешного POST выполняется перенаправление 303, поэтому обновление списка не создаёт повторную запись. При ошибке полей возвращается HTML 400, при отсутствии студента — 404.

### 8. Запуск и ручная проверка

Из корня проекта в Windows PowerShell:

```powershell
bun.cmd install
bun.cmd run start
```

Предварительно создавать SQL-таблицы или запускать Сервис 2 не требуется. Для изменения файла БД перед запуском можно установить переменную:

```powershell
$env:LAB8_DATABASE_PATH = 'testdb/security.sqlite'
bun.cmd run start
```

Путь DATABASE_PATH относится к предыдущим лабораторным; он должен отличаться от LAB8_DATABASE_PATH. Для просмотра новых таблиц в DBeaver используется подключение SQLite к файлу ЛР8.

Последовательность проверки:

1. Открыть http://localhost:8082/lab8 и перейти к регистрации.
2. Заполнить имя, фамилию, email и пароль, получить сообщение об успехе.
3. Проверить, что повторная регистрация с тем же email отклоняется.
4. Перейти ко входу, сначала проверить неверный пароль, затем войти с правильным.
5. Открыть список пользователей и убедиться, что регистрационные данные отображаются без пароля.
6. Добавить студента, изменить его возраст, проверить результат в списке.
7. Перезапустить приложение и проверить сохранённые данные.
8. В DBeaver открыть users, roles, user_roles и students. В users поле password_hash должно содержать хеш Argon2id.
9. Нажать «Выйти», затем снова открыть /lab8/list и убедиться в перенаправлении на вход.

### 9. Проверки Postman и автоматические тесты

В postman/lab8.postman_collection.json подготовлен последовательный сценарий. Cookie ведётся стандартным механизмом Postman, CSRF извлекается из HTML, для регистрации генерируется уникальный email. Автоматические перенаправления выключены, чтобы проверять ответ 303. Проверяется регистрация, повторный email, неверный пароль, вход, список пользователей, отказ без CSRF, CRUD студента и выход. Созданный сценариями студент удаляется, учебная учётная запись остаётся в БД.

```powershell
bun.cmd test tests/lab8.test.ts
bun.cmd test
bun.cmd run typecheck
```

18 тестов ЛР8 используют реальные HTTP-серверы и временные файловые БД. Проверяются хеширование, регистрация и конкурентная уникальность email, вход, роли и many-to-many, CSRF, cookie-флаги и ротация сессий, завершение и истечение сессий, сохранение после перезапуска, защищённый CRUD и экранирование. Проверяется также изоляция данных новой версии, ошибки БД и доступность прежних маршрутов. Пользовательские файлы БД не изменяются.
