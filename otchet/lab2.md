## Цель работы

Разработать простой REST-сервис, описать входящее и исходящее сообщения, добавить проверку полей запроса и обработку собственных исключений. Проверить работу сервиса HTTP-запросами.

## Описание задачи

По методичке необходимо реализовать POST-обработчик, который принимает JSON с идентификаторами сообщения и операции, временем и дополнительными полями. Сервис должен вернуть идентификаторы и результат обработки. Неправильные данные должны отклоняться с сообщением об ошибке. Дополнительное задание — собственное исключение UnsupportedCodeException при uid, равном строке «123».

Java-пример выполнен на стеке существующего проекта: TypeScript, Bun и Elysia. Все лабораторные находятся в одном репозитории и одной ветке main. Для ЛР2–3 используется POST /api/v2/feedback на порту 8082.

Этап ЛР2 сохранён в коммите 5e79a11 (lr-2). В текущей ветке тот же обработчик дополнен перечислениями и логированием ЛР3, а затем отрефакторен в ЛР4–5. Ниже отдельно отмечено поведение ЛР2 и последующие дополнения. Новая ветка для отчёта не создавалась.

### 2. Модель входящего сообщения

| Поле | Тип | Проверка ЛР2 |
| --- | --- | --- |
| uid | Строка | Обязательно, до 32 символов, не пустое и не только пробелы |
| operationUid | Строка | Обязательно, до 32 символов |
| systemName | Строка | Необязательно; в ЛР3 заменено на перечисление |
| systemTime | Строка | Обязательно |
| source | Строка | Необязательно |
| communicationId | Целое число | Обязательно, от 1 до 100000 включительно |
| templateId | Целое число | Необязательно |
| productCode | Целое число | Необязательно |
| smsCode | Целое число | Необязательно |

Фрагмент модели на этапе ЛР2, src/routes/v2/feedback/model.ts:

```typescript
export const FeedbackModelRequest = t.Object({
    uid: t.String({ maxLength: 32, pattern: '\\S' }),
    operationUid: t.String({ maxLength: 32 }),
    systemName: t.Optional(t.String()),
    systemTime: t.String(),
    source: t.Optional(t.String()),
    communicationId: t.Integer({ minimum: 1, maximum: 100000 }),
    templateId: t.Optional(t.Integer()),
    productCode: t.Optional(t.Integer()),
    smsCode: t.Optional(t.Integer()),
})
```

t.Optional разрешает отсутствие поля. Если необязательное поле передано, его тип всё равно проверяется. Например, source не может быть числом, а templateId — дробным числом.

Для operationUid проверяются наличие, строковый тип и максимальная длина. Пустая строка разрешена, поскольку запрет пустого значения в задании отдельно установлен для uid. Для входящего systemTime проверяются наличие и строковый тип; отдельная проверка календарной даты не реализована. В ответе время формируется сервером.

В текущей общей версии systemName допускает только ERP, CRM или WMS — это дополнение ЛР3. Поэтому в запросах для проверки ЛР2 это поле можно не передавать. Пустая строка systemName из примера методички в текущей версии не проходит перечисление.

### 3. Модель ответа

| Поле | Содержимое |
| --- | --- |
| uid | Идентификатор сообщения из запроса |
| operationUid | Идентификатор операции из запроса |
| systemTime | Время формирования ответа сервером |
| code | success или failed |
| errorCode | Пустая строка либо код ошибки |
| errorMessage | Пустая строка либо сообщение об ошибке |

В успешном ответе code равен success, а поля ошибки пустые. При ошибке code равен failed. Для ошибок валидации используется ValidationException, для запрещённого uid — UnsupportedCodeException, для непредвиденной ошибки — UnknownException.

Пример корректного запроса:

```json
{
  "uid": "message-2",
  "operationUid": "operation-2",
  "systemTime": "2026-10-28T12:00:00.000Z",
  "communicationId": 100,
  "templateId": 8,
  "productCode": 1500,
  "smsCode": 10
}
```

Пример структуры успешного ответа:

```json
{
  "uid": "message-2",
  "operationUid": "operation-2",
  "systemTime": "2026-10-28T12:00:00.123Z",
  "code": "success",
  "errorCode": "",
  "errorMessage": ""
}
```

Значение systemTime в примере условное: при каждом запросе сервер устанавливает текущее время. Идентификаторы сообщения и операции сохраняются.

### 4. Контроллер и валидация

На этапе ЛР2 основная часть обработчика выглядела следующим образом:

```typescript
const validationService = new RequestValidationService()

export const feedback = new Elysia({ prefix: '/feedback' })
    .post('', ({ body }) => {
        validationService.isValid([])
        if (body.uid === '123') {
            throw new UnsupportedCodeException('uid 123 не поддерживается')
        }
        return {
            uid: body.uid,
            operationUid: body.operationUid,
            systemTime: new Date().toISOString(),
            code: 'success',
            errorCode: '',
            errorMessage: '',
        }
    }, {
        body: FeedbackModelRequest,
        // Схемы ответов и обработчик ошибок описаны в полном файле.
    })
```

До вызова основной функции Elysia проверяет body по схеме. Поэтому при правильном запросе сервис получает пустой список ошибок. Если схема отклонила данные, вызывается обработчик error, который передаёт ошибки в RequestValidationService.

Интерфейс и реализация на этапе ЛР2:

```typescript
export interface ValidationService {
    isValid(errors: readonly string[]): void
}

export class RequestValidationService implements ValidationService {
    isValid(errors: readonly string[]): void {
        if (errors.length > 0) {
            throw new ValidationFailedException(errors[0])
        }
    }
}
```

Обработчик преобразует исключение в JSON. При ValidationFailedException возвращается HTTP 400, errorCode = ValidationException и errorMessage = «Ошибка валидации». Данные не проходят к успешному ответу.

В актуальном коде формирование успешного ответа и общего ответа об ошибке вынесено в FeedbackResponseService. Это последующий рефакторинг ЛР5; внешний контракт ЛР2 сохранён.

### 5. Собственное исключение для uid = 123

В exception.ts объявлен класс UnsupportedCodeException, унаследованный от Error. После проверки схемы контроллер сравнивает uid со строкой «123» и выбрасывает это исключение. Обработчик ошибки возвращает HTTP 400:

```json
{
  "uid": "123",
  "operationUid": "operation-2",
  "systemTime": "2026-10-28T12:00:00.123Z",
  "code": "failed",
  "errorCode": "UnsupportedCodeException",
  "errorMessage": "Не поддерживаемая ошибка"
}
```

Время условное. Текст errorMessage сохранён в точности как в коде проекта. Если запрос одновременно нарушает схему, сначала обрабатывается ошибка валидации.

## Ответы на контрольные вопросы

По условию чётному номеру в списке соответствуют чётные вопросы, нечётному — нечётные. Ниже приведены ответы на все шесть вопросов.

### 1. Чем GET отличается от POST?

GET запрашивает представление ресурса. По HTTP его назначение безопасно и идемпотентно: повторный запрос не должен означать повторную операцию изменения данных. POST передаёт содержимое для обработки указанным ресурсом; результат зависит от приложения, например создание записи или расчёт. POST в общем случае не является идемпотентным. В нашей работе JSON передаётся через POST [1].

### 2. Какое содержимое можно передавать POST-запросом?

Можно передавать JSON, XML, текст, данные формы, файлы через multipart/form-data и двоичные данные. Формат обозначается заголовком Content-Type и должен поддерживаться серверным обработчиком. В проекте используется application/json. Сам метод POST не ограничен JSON [1].

### 3. Чем XML отличается от JSON?

XML представляет данные с помощью элементов, тегов и атрибутов, поддерживает пространства имён. JSON использует объекты, массивы, строки, числа, логические значения и null. Оба формата текстовые и могут описывать вложенные данные. В данном API применяется JSON, который удобно преобразуется в объекты TypeScript [2, 3].

### 4. Зачем нужны собственные исключения?

Они позволяют отличать известные причины ошибок и обрабатывать их отдельно. В этой работе ValidationFailedException обозначает неправильные поля, а UnsupportedCodeException — специальный запрет uid = 123. Контроллер назначает соответствующий HTTP-статус и код ответа вместо одинакового сообщения для всех сбоев.

### 5. Что означает @Service?

В Spring это аннотация компонента сервисного слоя, специализация @Component. При настройке сканирования Spring может обнаружить такой класс и зарегистрировать его как управляемый компонент. В нашем TypeScript-проекте аннотация не используется: объект RequestValidationService создаётся явно через new [4].

### 6. Что означает @RestController?

Это составная аннотация Spring, объединяющая @Controller и @ResponseBody. Возвращаемое значение метода передаётся в тело HTTP-ответа с помощью механизма преобразования сообщений. Например, объект может быть сериализован в JSON. В Elysia похожую роль выполняет .post(), возвращающий объект ответа [5].
