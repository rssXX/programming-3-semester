Разработать REST-сервис для работы с реляционной базой данных: реализовать создание, чтение, изменение и удаление записей, разделить приложение на контроллеры, сервисы, DAO и сущности. Реализовать дополнительные задания для таблицы учебных дисциплин и единый ответ о результате операции.

## Описание задачи

Создать файловую БД с таблицей студентов. Сущность студента содержит идентификатор, имя, фамилию, факультет и возраст. Реализовать REST-операции GET списка, GET по идентификатору, POST, PUT и DELETE. Для PUT передавать идентификатор в теле запроса, как в методичке.

### 2. Создание и настройка базы данных

Схема находится в `src/database/schema.sql`:

```sql
CREATE TABLE IF NOT EXISTS students (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL CHECK (length(trim(name)) BETWEEN 1 AND 15),
    surname TEXT NOT NULL CHECK (length(trim(surname)) BETWEEN 1 AND 25),
    faculty TEXT NOT NULL CHECK (length(trim(faculty)) BETWEEN 1 AND 20),
    age INTEGER NOT NULL CHECK (age BETWEEN 0 AND 150)
) STRICT;

CREATE TABLE IF NOT EXISTS disciplines (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL CHECK (length(trim(name)) BETWEEN 1 AND 100),
    hours INTEGER NOT NULL CHECK (hours BETWEEN 1 AND 10000)
) STRICT;
```

Ограничения длины полей студента соответствуют `varchar(15)`, `varchar(25)` и `varchar(20)` из задания. `INTEGER PRIMARY KEY AUTOINCREMENT` заменяет H2 `AUTO_INCREMENT`. Добавлены обязательность полей и проверки допустимых значений. `STRICT` ограничивает типы хранимых данных.

Состав полей учебной дисциплины методичка не задаёт. В рамках работы выбраны `id`, `name` и `hours`: идентификатор, название и объём в учебных часах. Связь между студентами и дисциплинами в задании не требуется; таблицы используют независимые идентификаторы.

Класс `ApplicationDatabase` в `src/database/index.ts` управляет соединением. По умолчанию файл расположен в `testdb/students.sqlite`. Путь берётся из `DATABASE_PATH`; для изолированных тестов также передаётся параметр `databasePath` в `createApp`.

Соединение открывается лениво при первом обращении к DAO. При этом создаётся каталог, открывается файл и в транзакции выполняется идемпотентный SQL-скрипт схемы. Включена проверка внешних ключей и установлен `busy_timeout = 5000`. При остановке HTTP-приложения соединение закрывается через `onStop`. Вызов маршрутов прежних работ не создаёт файл БД.

Для явной инициализации и заполнения предусмотрены команды:

```sh
bun install
bun run db:init
bun run db:seed
bun run start
```

`db:init` создаёт обе таблицы. Необязательная команда `db:seed` выполняет `src/database/seed.sql`: добавляет двух студентов и две дисциплины, включая «Базы данных». Перед вставкой проверяется наличие демонстрационной записи, поэтому повторный запуск не дублирует её и не очищает пользовательские данные.

Пример выбора другого файла в Windows PowerShell:

```powershell
$env:DATABASE_PATH = 'testdb/my-students.sqlite'
bun.cmd run db:init
bun.cmd run db:seed
bun.cmd run start
```

В DBeaver следует выбрать подключение SQLite и указать абсолютный путь к созданному файлу. Подключение H2 из методички не подходит для файла SQLite. Локальная БД и её служебные файлы исключены из Git; схема и демонстрационные данные хранятся в репозитории как SQL-скрипты.

### 4. Сущность и схемы студента

Сущность описывает строку таблицы, а тип `StudentData` используется при создании без идентификатора:

```typescript
export interface Student {
    id: number
    name: string
    surname: string
    faculty: string
    age: number
}

export type StudentData = Omit<Student, 'id'>
```

HTTP-схемы находятся в `students/model.ts`. Например, возраст задан как `t.Integer({ minimum: 0, maximum: 150 })`. Для текстовых полей применены ограничения длины и шаблон `\S`, требующий хотя бы один непробельный символ. В схему PUT включён положительный целочисленный `id` не больше `Number.MAX_SAFE_INTEGER`.

Схемы используются для валидации входящего JSON, вывода типов обработчиков и генерации OpenAPI. Это соответствует возможностям [схем Elysia](https://elysiajs.com/essential/validation).

### 5. DAO и сервис студентов

Интерфейс DAO определяет пять операций:

```typescript
export interface StudentDAO {
    findAll(): Student[]
    findById(id: number): Student | null
    create(student: StudentData): Student
    update(student: Student): Student | null
    delete(id: number): boolean
}
```

В `SqliteStudentDAO` чтение списка выполняется с `ORDER BY id`. Поиск отсутствующей записи возвращает `null`, а удаление проверяет число изменённых строк. Вставка и обновление используют `RETURNING`, чтобы вернуть фактически сохранённые данные.

Пример обновления:

```typescript
update(student: Student): Student | null {
    return this.connection.database.query<Student,
        [string, string, string, number, number]>(
        'UPDATE students SET name = ?, surname = ?, faculty = ?, '
        + 'age = ? WHERE id = ? RETURNING id, name, surname, faculty, age',
    ).get(student.name, student.surname, student.faculty,
        student.age, student.id)
}
```

Значения передаются параметрами вместо подстановки в SQL. Например, строка с кавычками хранится как обычное значение, а не выполняется как команда.

`StudentServiceImpl` обрезает пробелы в текстовых полях и обрабатывает результат DAO. Метод PUT изменяет только существующую запись:

```typescript
update(student: Student): Student {
    const result = this.dao.update({
        ...this.normalize(student), id: student.id,
    })
    if (!result) {
        throw new ResourceNotFoundError(
            `Студент с id=${student.id} не найден`,
        )
    }
    return result
}
```

Аналогичная проверка выполнена для чтения по `id` и удаления. Отсутствующий `id` не приводит к созданию новой записи или успешному сообщению об удалении.

### 6. Контроллеры и HTTP-контракт

Контроллеры находятся в `students/index.ts` и `disciplines/index.ts`. Они регистрируют маршруты, передают данные сервисам, устанавливают HTTP-статус и оборачивают результат в общий формат. Пример POST студента:

```typescript
.post('', ({ body, set }) => {
    const student = service.create(body)
    set.status = 201
    return success(student, 'Студент создан')
}, {
    body: StudentCreateModel,
    response: { 201: SuccessResponse(StudentModel), ...errors },
    detail: { tags: ['ЛР6: студенты'] },
})
```

Маршруты Сервиса 1:

| Метод | Студенты | Учебные дисциплины | Действие |
| --- | --- | --- | --- |
| GET | `/api/v5/students` | `/api/v5/disciplines` | Получить все записи |
| GET | `/api/v5/students/{id}` | `/api/v5/disciplines/{id}` | Получить запись по id |
| POST | `/api/v5/students` | `/api/v5/disciplines` | Создать запись |
| PUT | `/api/v5/students` | `/api/v5/disciplines` | Обновить запись, id в JSON |
| DELETE | `/api/v5/students/{id}` | `/api/v5/disciplines/{id}` | Удалить запись |

Пример `POST http://localhost:8082/api/v5/students` с `Content-Type: application/json`:

```json
{ "name": "Иван", "surname": "Иванов", "faculty": "ИТ", "age": 25 }
```

Пример ответа HTTP 201 (конкретный `id` назначает БД):

```json
{
  "success": true,
  "message": "Студент создан",
  "data": {
    "id": 1,
    "name": "Иван",
    "surname": "Иванов",
    "faculty": "ИТ",
    "age": 25
  }
}
```

Для PUT отправляется полный набор полей и существующий `id`:

```json
{ "id": 1, "name": "Иван", "surname": "Иванов", "faculty": "РТФ", "age": 26 }
```

После удаления `DELETE /api/v5/students/1` успешный ответ содержит `data: { "id": 1 }`. Последующий GET удалённой записи возвращает HTTP 404:

```json
{
  "success": false,
  "message": "Студент с id=1 не найден",
  "data": null
}
```

Таким образом выполнено дополнительное требование: ответ каждой операции явно сообщает об успехе или неуспехе, включая операции изменения и удаления. Успешный пустой список возвращается как `success: true`, `data: []`.

| HTTP-статус | Условие |
| --- | --- |
| 200 | Успешные GET, PUT и DELETE |
| 201 | Успешный POST |
| 400 | Невалидные поля, недопустимый id, отсутствующие обязательные поля или повреждённый JSON |
| 404 | Запись не найдена при GET по id, PUT или DELETE |
| 500 | Ошибка открытия или выполнения операции с БД |

Общий обработчик `crudError` сопоставляет ошибку сервисного слоя с 404, ошибки `VALIDATION` и `PARSE` — с 400. Для остальных ошибок возвращается сообщение «Ошибка работы с базой данных», а подробности записываются через consola в серверный лог. В HTTP-ответ не включаются путь к файлу и текст SQL-ошибки.

Интерактивная документация: `http://localhost:8082/openapi`. Спецификация JSON: `http://localhost:8082/openapi/json`. Для ЛР6 добавлены отдельные теги студентов и дисциплин и схемы успешных и ошибочных ответов.

### 1. Чем отличаются реляционные БД от документоориентированных? Примеры СУБД

Реляционная БД представляет данные как таблицы из строк и столбцов. Схема определяет структуру таблиц, ключи и ограничения. Связанные данные обычно распределяются между таблицами и объединяются запросами, например через JOIN. Примеры: PostgreSQL, MySQL и SQLite.

Документоориентированная БД хранит документы, например JSON или BSON, со вложенными объектами и массивами. Документы одной коллекции могут иметь различную структуру, если ограничения схемы не заданы отдельно. Часто связанные данные размещают внутри одного документа. Примеры: MongoDB и Apache CouchDB. Наличие транзакций или проверки схемы зависит от СУБД; эти возможности не ограничены только реляционными БД.

В работе SQLite выбрана для таблиц с явно заданными полями, ключами и ограничениями.

### 2. Что представляют собой подходы API-First и Code-First?

При API-First сначала проектируют и согласовывают контракт API: маршруты, модели сообщений, статусы и правила ошибок. Например, создают спецификацию OpenAPI, по которой клиенты и сервер разрабатываются параллельно. Контракт используют для документации, генерации кода и проверок совместимости.

При Code-First сначала реализуют маршруты, модели и обработчики в коде, а описание API получают из этой реализации. В данном проекте применён Code-First: схемы Elysia задают контракт запросов и ответов, а плагин `@elysia/openapi` формирует спецификацию. В обоих подходах контракт должен соответствовать реальному поведению сервера.

### 3. Что такое Swagger?

Swagger — набор инструментов для описания, визуализации и использования HTTP API. Swagger Editor помогает редактировать описание, Swagger UI отображает интерактивную документацию, Swagger Codegen генерирует клиентский и серверный код. Формат описания API, исторически связанный со Swagger, развивается как OpenAPI Specification.

В проекте спецификация OpenAPI формируется из маршрутов и схем Elysia. Страница `/openapi` использует интерфейс, предоставляемый плагином; совместимость со спецификацией OpenAPI не означает, что используется именно Swagger UI. См. [описание OpenAPI и инструментов Swagger](https://swagger.io/docs/specification/v3_0/about/).

### 4. Какие существуют виды интеграции информационных систем?

Можно выделить несколько распространённых способов обмена:

- Файловый обмен: системы передают CSV, JSON, XML или другие файлы. Подходит для пакетной обработки, но данные поступают с задержкой.
- Общая БД: несколько систем используют одни таблицы или представления. Доступ к данным прямой, однако системы зависят от общей схемы и правил записи.
- Сервисные вызовы: система обращается к REST, SOAP или RPC API другой системы. Удобны для получения результата по запросу; синхронные вызовы зависят от доступности получателя.
- Очереди сообщений и события: системы публикуют и получают сообщения через брокер. Обмен может быть асинхронным, с буферизацией и повторной доставкой; потребители должны учитывать дубликаты.

По организации связей также различают прямую интеграцию «точка-точка», обмен через центральный интеграционный узел или шину и событийную архитектуру. Это другая классификация: например, API-вызов может быть и прямым, и проходить через посредника. В ЛР4 использован прямой HTTP-вызов двух сервисов, а в ЛР6 API предоставляет клиенту доступ к операциям над БД.

### 5. Чем отличаются SOAP и REST?

SOAP — протокол обмена структурированными сообщениями с определённым XML-конвертом. Его расширения применяются для дополнительных требований, например безопасности сообщений. SOAP может использовать различные транспортные протоколы, включая HTTP. Формат и обработка сообщения определены [спецификацией SOAP](https://www.w3.org/TR/soap12-part1/).

REST — архитектурный стиль с ресурсами, единообразным интерфейсом и отсутствием серверной сессии, необходимой для понимания отдельного запроса. В HTTP API ресурсы обычно адресуются URL, а операции выражаются методами GET, POST, PUT и DELETE. Представление ресурса может быть JSON, XML и другого типа: JSON не является обязательным условием REST.

Таким образом, SOAP задаёт протокол сообщений, а REST — ограничения архитектуры. В данной работе HTTP API использует JSON и стандартные методы и статусы HTTP.

### 6. Что такое gRPC и в чём его отличие от REST?

gRPC — фреймворк удалённого вызова процедур. Обычно контракт сервиса и сообщений задаётся в `.proto` через Protocol Buffers; по нему генерируются клиентские и серверные интерфейсы. Клиент вызывает метод сервиса, а библиотека выполняет передачу и сериализацию. Поддерживаются одиночный ответ, поток ответов сервера, поток запросов клиента и двунаправленный поток. См. [основные концепции gRPC](https://grpc.io/docs/what-is-grpc/core-concepts/).

В gRPC взаимодействие организовано вокруг методов сервиса, а в REST — вокруг ресурсов и единообразных операций. Нативный протокол gRPC использует HTTP/2 и обычно двоичную сериализацию Protocol Buffers; REST не фиксирует формат представления и также может работать поверх HTTP/2. Типичный REST API с JSON удобен для прямой проверки HTTP-инструментами, а gRPC предоставляет генерацию типизированных клиентов и встроенные варианты потокового обмена. Различие не сводится к версии HTTP или формату JSON. Транспорт gRPC описан в [документации проекта](https://github.com/grpc/grpc/blob/master/CONCEPTS.md).
